# mwaveform 当前实现问题清单与协议优化建议

日期：2026-08-07

本文基于当前工作区源码进行静态检查，范围包括：

- `AddVariable`、`AddChannel`、`Push`、`Step` 和采样分频；
- `SnapshotStart`、`SnapshotFeed`、`SnapshotTrigger`；
- waveform 帧格式、兼容格式和 RTT 发送路径。

“源码确认”表示可以直接从当前控制流推导；“需要实机验证”表示还需要使用 MStudio 或原始 RTT 抓包确认最终表现。

## 一、优先处理的问题

### 1. Snapshot 的通道 mask 可能为空

状态：源码确认，建议优先修复并用原始帧验证。

涉及代码：

- `modus/src/mdebug/mwaveform.c:293-313`：`Step()` 生成临时的
  `abSampleMask`，并在结束时清除 `s_tWave.abMask`；
- `modus/src/mdebug/mwaveform.c:618-632`：`SnapshotFeed()` 复制的是
  `s_tWave.abMask`，而不是本次 `Step()` 生成的 `abSampleMask`。

当前工程的调用顺序是：

```c
mwaveform.Step();
mwaveform.SnapshotFeed();
```

因此，`SnapshotFeed()` 执行时，`Step()` 可能已经把 `abMask` 清零。对于
`AddVariable`，`abMask` 本来就不是由变量读取逻辑设置的；对于
`AddChannel + Push`，`Step()` 消费后也会清除对应位。

快照打包时会根据 mask 决定是否输出每个通道的数据，所以可能出现“缓存里有数值，但上位机认为该通道无效”的现象。

建议：在快照样本中保存本次实际采样的 mask，或者让 `SnapshotFeed()` 接收
`Step()` 产生的有效 mask；不要直接复用普通实时流的待消费 `abMask`。

### 2. Snapshot 的采样频率可能与变量刷新频率不一致

状态：当前工程配置下源码确认。

当前配置为：

```c
mwaveform.SetStreamRate(50000, 10000);  /* 20 kHz ISR，10 kHz stream */
```

这会让 `Step()` 每两个 ISR 调用才生成一个 stream 样本，但当前
`phase_test_waveform_hf_step()` 仍然在每个 20 kHz ISR 调用 `SnapshotFeed()`。

结果可能是：

- `SnapshotFeed()` 的调用频率是 20 kHz；
- `AddVariable` 的缓存值只在 `Step()` 真正采样时更新，实际约 10 kHz；
- `wSampleIndex` 也只在 `Step()` 生成样本时递增，快照中可能出现重复样本序号。

因此，`SnapshotStart(..., 50000)` 不能单独保证快照是有效的 20 kHz 数据。
快照需要独立的采样节拍，或者需要让参与快照的变量在每次
`SnapshotFeed()` 前都完成更新。

### 3. Snapshot 未填满就触发时，仍发送完整深度

状态：源码确认。

`SnapshotStart()` 将写指针清零，但 `SnapshotTrigger()` 和 `Poll()` 没有保存“已经写入了多少个有效样本”。触发后，`Poll()` 总是使用
`hwSnapshotDepth` 作为发送样本数：

```c
mwaveform_pack_snapshot(...,
                        s_tWave.hwSnapshotDepth,
                        s_tWave.hwSnapshotDepth, ...);
```

如果刚 arm 就触发，剩余位置可能是零值、上一次快照的残留值或未初始化语义的数据。

建议增加 `hwSnapshotValidCount`：

- 缓冲未写满时发送有效样本数；
- 缓冲写满后发送完整深度；
- 上位机根据帧中的有效样本数解析。

### 4. `SnapshotStop()` 可能丢弃已经触发但尚未发送的快照

状态：源码确认。

`SnapshotTrigger()` 只是设置 ready 标志，随后由 `Poll()` 打包并设置
`bSnapshotPending`。如果此时调用 `SnapshotStop()`，它会直接清除
`bSnapshotPending`，导致待发送帧被丢弃。

建议：

- `SnapshotStop()` 只停止后续采集，不清除待发送帧；或
- 提供明确的 `SnapshotCancel()`；或
- 文档明确要求等待 `Poll()` 完成后再 stop。

### 5. `SnapshotStart()` 的深度可能被静默截断

状态：源码确认，属于接口可观测性问题。

`SnapshotStart()` 会把请求深度限制在：

- `MWAVEFORM_SNAPSHOT_DEPTH`；
- 当前 RTT 缓冲区可以容纳的最大深度。

但函数只返回成功/失败，不返回实际深度。当前 shell 命令打印的也是用户请求值，而不是固件截断后的值。

例如当前工程配置 `MWAVEFORM_SNAPSHOT_DEPTH = 16` 时：

```text
wave snap start 32 50000
```

实际最多记录 16 点，但日志可能仍显示 32 点。

建议让 `SnapshotStart()` 返回实际深度，或新增查询接口/状态字段。

## 二、采样接口和使用上的风险

### 6. `SetRate()` 与 `SetStreamRate()` 容易造成驱动模式误配置

`SetStreamRate()` 会设置 stream 分频和元数据周期，但不会自动切换到外部驱动模式。
如果调用了 `SetStreamRate()`，却没有调用：

```c
mwaveform.SetRate(0);
```

则默认 `modus_Clock()` 仍可能按系统时钟调用 `Step()`。此时上报的 stream 周期和实际 `Step()` 频率可能不一致。

建议：

- 外部 ISR 驱动时，将 `SetRate(0)` 和 `SetStreamRate()` 作为固定初始化组合；
- 非外部驱动时，不要再从高频 ISR 手动调用 `Step()`；
- 在接口或日志中显示当前驱动模式和实际 `Step()` 计数。

### 7. `AddChannel + Push` 在一次 `Step()` 前多次更新时只保留最后值

这是当前接口的设计行为，不一定是 bug。`Push()` 更新单个缓存槽并设置 mask，不会排队保存每次调用的值。

因此如果两个 `Step()` 之间调用多次 `Push()`，中间值会丢失。需要保留每个高频点时，应使用独立的采样环或让 `Push()` 与采样节拍一一对应。

### 8. `SetChannelRate()` 是分频，不是独立采样调度器

`SetChannelRate()` 对 `AddVariable` 和 `AddChannel` 都适用。它只决定某个通道在 stream 样本中何时被纳入，不能：

- 把通道频率提高到超过 stream 频率；
- 自动调用 `Push()`；
- 让 `AddVariable` 在 `Step()` 之外自动刷新。

实际通道频率还受 `Push()` 或绑定变量更新频率限制。

## 三、协议帧现状与必要性判断

### 9. 当前“多种帧头”实际上是统一同步字节加类型

当前协议使用统一同步字节：

```text
AA 55
```

第三字节区分帧类型：

| 类型 | 当前值 | 用途 |
| --- | ---: | --- |
| DESC | `0xFD` | 通道名称和缩放系数 |
| META | `0xFE` | 版本、通道数、采样周期、batch 深度 |
| BATCH | `0xFC` | 连续实时流样本 |
| SNAPSHOT | `0xFA` | 触发式快照样本 |
| 旧单点帧 | 序号 | 兼容旧的单点数据格式 |

DESC、META、BATCH、SNAPSHOT 的 payload 结构不同，因此保留类型字段是有必要的。
没有必要为每种帧设计完全不同的同步字节；当前 `AA 55 + type` 的方向是合理的。

### 10. 旧单点帧的序号可能与保留类型冲突

状态：旧兼容路径存在源码风险；当前工程启用 batch 模式时通常不会触发。

旧单点帧把第三字节同时当作序号，而 `0xFA`、`0xFC`、`0xFD`、`0xFE` 又是保留帧类型。当前代码在遇到保留值时只自增一次，例如从 `0xFC` 自增到 `0xFD`，仍然会落入保留类型。

建议：

- 使用“递增直到离开保留集合”的逻辑；或
- 旧单点帧增加明确的 `LEGACY_DATA` 类型；或
- batch 模式稳定后删除旧单点帧发送路径。

### 11. 帧格式缺少统一长度字段

DESC、META、BATCH、SNAPSHOT 目前依靠帧类型和内部字段推导长度，旧单点帧则依靠 mask 和通道数推导长度。

这在无丢字节的情况下可以工作，但在 RTT/TCP 分段、串流重同步或协议扩展时，解析器会更复杂。统一长度字段可以让接收端：

- 更快跳过坏帧；
- 在未知类型时安全跳过；
- 检查长度是否超过缓冲区；
- 支持未来扩展字段。

### 12. CRC8 实现较弱且各类帧不统一

当前 descriptor/meta/旧单点帧使用 XOR 风格的 CRC8，batch/snapshot 使用 CRC16。
这不是立即的功能 bug，但对高频 RTT 链路的误码检测能力不一致。

协议 V2 可以统一使用 CRC16。若必须保持头部开销，则至少应使用标准多项式 CRC8，而不是简单 XOR。

### 13. Descriptor 发送失败时没有立即重试

`send_descriptor_frame()` 直接调用 `SEGGER_RTT_Write()`，不检查是否完整写入；同时 `Poll()` 在发送前就清除 `bRequestDesc`。

如果 RTT 空间不足，descriptor 可能丢失，只能等待下一次周期性 descriptor 发送。
建议采用与 metadata 相同的“写成功后清除请求”策略，并统计失败次数。

## 四、协议优化建议

### 推荐方案：保留 V1，增量修复；另规划 V2

不建议仅为了“帧头看起来统一”而立刻替换当前协议，因为 MStudio 端需要同步升级，且现有类型区分本身有实际用途。

推荐分两阶段：

#### 阶段一：V1 兼容修复

1. 先修复 Snapshot 的有效 mask、有效样本数和 pending 生命周期。
2. 修复旧单点帧序号避让逻辑，或在 batch 模式下禁用旧单点帧。
3. descriptor 写入失败时保留重试标志。
4. 在 status/meta 中报告实际 snapshot 深度和实际采样模式。
5. 保持 `AA 55 + type`，避免破坏现有 MStudio 解析器。

#### 阶段二：协议 V2

建议统一为：

```text
SYNC(AA55)
VERSION
TYPE
FLAGS
PAYLOAD_LEN(u16)
SEQUENCE(u32)
PAYLOAD
CRC16
```

其中 `TYPE` 继续区分 descriptor、metadata、batch 和 snapshot。这样统一的是帧封装，不是把所有 payload 强行合并。

V2 需要配套：

- MStudio 端版本协商或明确协议版本；
- V1/V2 并行解析过渡期；
- 长度边界、未知类型、CRC 错误和丢序号测试；
- 对 RTT 分段和半帧输入的解析器测试。

## 五、建议的验证用例

在修改代码前，建议先加入或手工验证以下场景：

1. `SnapshotStart()` 后只 Feed 1 点就 Trigger，确认不会发送未写入样本。
2. 分别使用 `AddVariable` 和 `AddChannel + Push`，检查 snapshot mask 和数值是否都能被 MStudio 解码。
3. `SetStreamRate(20 kHz, 10 kHz)` 时确认 snapshot 的实际样本序号、数值更新时间和声明周期一致。
4. Trigger 后立即 Stop，确认待发送 snapshot 不会丢失。
5. RTT 写满时确认 descriptor、metadata、batch、snapshot 的重试行为一致。
6. 关闭 batch 模式并让旧单点序号跨过 `0xFA/0xFC/0xFD/0xFE`，确认不会被误判为控制帧。

## 结论

当前多种帧类型本身是有必要的，问题不在于 `AA 55` 出现多次，而在于旧单点帧复用序号、缺少统一长度、CRC 强度不一致以及部分发送失败处理不一致。

优先级应是：先修 Snapshot 数据正确性，再做 V1 兼容修复，最后在 MStudio 可同步升级的前提下引入统一封装的协议 V2。
